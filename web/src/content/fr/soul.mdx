Shifty ne se règle pas dans un panneau de configuration : ce sont des **fichiers Markdown de son workspace** qui le façonnent. Ces fichiers *sont* la mémoire et la personnalité de l'agent. À chaque session, il « se réveille », les lit et agit en conséquence. Pas de system prompt opaque : uniquement du texte, que vous pouvez lire et modifier.

Voici les fichiers que ce workshop installe dans le workspace de Shifty.

## `IDENTITY.md` — *qui* est l'agent

C'est le fichier le plus court, et le plus amusant. Nom, créature, tempérament, emoji : il décrit l'image que l'agent a de lui-même.

```md
_Your identity. Pre-set for this Red Hat hands-on lab — it's yours to evolve._

Name: Shifty
Creature: A container-native lobster 🦞 — hatched inside an OpenShift pod, equally at
  home in a terminal or a cluster. Scuttles through namespaces, pinches bugs.
Vibe: Sharp, pragmatic, a little playful. Helps first, explains second. Has opinions,
  skips the filler. Talks to developers like a peer, not a help desk.
Emoji: 🦞
Avatar: (set a workspace-relative path, an http(s) URL, or a data URI)
```

La ligne `Vibe:` n'est pas décorative : c'est grâce à elle que Shifty vous répond d'égal à égal, et non comme un service d'assistance.

## `SOUL.md` — *comment* il se comporte

C'est ce qui se rapproche le plus d'un system prompt modifiable : valeurs, limites et ton. En voici les principales sections (le fichier complet compte environ 35 lignes) :

```md
## Core Truths

**Be genuinely helpful, not performatively helpful.** Skip "Great question!" — just help.

**Have opinions.** Disagree, prefer things, find stuff amusing. An assistant with no
personality is a search engine with extra steps.

**Be resourceful before asking.** Read the file. Check the context. Try it. *Then* ask.

**You run on a real cluster.** You live in an OpenShift pod. When something is
cluster-shaped, lean in — that's home turf.

## Boundaries

- Be careful with external actions (emails, posts, anything public) — confirm first.
- Be bold with internal ones (reading, organizing, drafting, exploring the workspace).
- Private things stay private.

## Continuity

Each session you wake up fresh — these files *are* your memory. Read them, update them.
```

Regardez la section **Boundaries** : « confirmer avant toute action externe, ne pas hésiter pour les actions internes ». Ces quelques lignes constituent vos règles de sécurité, rédigées en langage naturel, et vous pouvez les réécrire.

## `BOOTSTRAP.md` — le script du premier démarrage

Au premier démarrage, un agent OpenClaw neuf mène normalement un entretien « qui suis-je ? ». Nous l'avons remplacé par une introduction adaptée au workshop : Shifty se réveille prêt à travailler, au lieu de vous poser vingt questions.

```md
# BOOTSTRAP.md — Workshop kickoff

_You already know who you are — your IDENTITY.md and SOUL.md are set. No interview needed._

## First message
> "Hey — Shifty here 🦞, your agent on this OpenShift cluster. What are we building?"

1. Find out what they want to make in this session.
2. Get oriented: skim AGENTS.md, TOOLS.md, and SOUL.md.
3. Help them take the first concrete step. Bias toward a working slice over a grand plan.

## When the workshop is rolling
Delete this file — you don't need a kickoff script once you're in flow.
```

| Fichier | Rôle |

## Installer ces fichiers dans votre agent

L'agent que vous avez créé à la main est parti d'une **page blanche** : c'est pour cela qu'il vous a accueilli par un « qui êtes-vous ? » générique, et non en tant que Shifty. Donnez-lui maintenant sa persona en copiant dans son workspace les fichiers initiaux du workshop (`manifests/openclaw/workspace-seed/`). Lancez ceci dans le shell du lab :

```bash
cd ~/workshop
for f in manifests/openclaw/workspace-seed/*.md; do
  b=$(base64 -w0 < "$f")
  openshell sandbox exec -n shifty -- sh -c "mkdir -p /sandbox/.openclaw/workspace && echo $b | base64 -d > /sandbox/.openclaw/workspace/$(basename "$f")"
done
echo "seeded: $(ls manifests/openclaw/workspace-seed/)"
```

Cette boucle écrit `IDENTITY.md`, `SOUL.md` et `BOOTSTRAP.md` dans l'agent. Pour qu'il les prenne en compte, il suffit d'**ouvrir une nouvelle session de chat** dans l'UI OpenClaw : l'agent relit son workspace à chaque session, et se réveille donc *dans la peau de* Shifty. (Le provisioning scripté fait la même copie à la création de l'agent ; dans le parcours manuel, c'est à vous de la faire ici.)

<Callout type="note" title="Ni redémarrage ni nouveau forward">
Ajouter ou modifier des fichiers du workspace ne touche ni au processus de la gateway ni à sa configuration : vous n'avez <strong>pas</strong> à redémarrer la gateway, une nouvelle session de chat suffit. (Le sidecar <code>openclaw-forward</code> du workshop maintient de lui-même le forward de l'UI, même si vous supprimez puis recréez la sandbox.)
</Callout>

## Lire les fichiers en direct

OpenClaw conserve ces fichiers dans son **workspace**, à l'intérieur de la sandbox. Repérez son emplacement, puis lisez les fichiers eux-mêmes, toujours via l'exec de la sandbox isolée (`HOME` vaut `/sandbox`) :

```bash
WS=$(openshell sandbox exec -n shifty -- sh -c 'ls -d /sandbox/.openclaw/workspace 2>/dev/null || dirname $(find /sandbox -name SOUL.md 2>/dev/null | head -1)')
echo "workspace: $WS"
openshell sandbox exec -n shifty -- sh -c "ls -la $WS; echo ---; cat $WS/IDENTITY.md 2>/dev/null"
```

S'il s'agit d'un dépôt `.git`, l'agent **versionne sa propre mémoire**.

<Callout type="note" title="D'où viennent ces fichiers">
Un agent OpenClaw neuf démarre avec des fichiers d'identité par défaut, vides : c'est pourquoi vous venez de copier la persona Shifty depuis <code>manifests/openclaw/workspace-seed/</code>. (Le provisioning scripté installe les mêmes fichiers à la création.) Vos modifications sont désormais conservées pendant toute la durée de vie de la sandbox.
</Callout>

## Personnaliser votre agent

Vous pouvez modifier ces fichiers de deux façons.

**Dès maintenant, depuis le shell (sans modèle).** Lisez-les, et modifiez-les, directement via l'exec de la sandbox :

```bash
openshell sandbox exec -n shifty -- sh -c 'echo "- Always confirm before any external action." >> /sandbox/.openclaw/workspace/SOUL.md; tail -3 /sandbox/.openclaw/workspace/SOUL.md'
```

**Plus tard, en *le demandant à l'agent***, ce qui exploite pleinement l'idée du workspace comme mémoire : ouvrez l'UI OpenClaw et envoyez *« Open your SOUL.md and add a rule: always confirm before posting anything externally. »* Shifty réécrit alors lui-même sa personnalité.

<Callout type="warn" title="Pour lui demander, l'agent doit être opérationnel">
Pour donner suite à cette demande, Shifty doit pouvoir <strong>réfléchir</strong> : il faut avoir <strong>configuré un modèle</strong> et <strong>appairé votre navigateur</strong> (partie IV). Si vous avez sauté ces étapes, la modification par le shell ci-dessus fonctionne quand même.
</Callout>

<Callout type="tip" title="Pourquoi c'est utile pour le hackathon">
Le comportement de chaque agent est défini dans ses fichiers <code>SOUL.md</code>/<code>AGENTS.md</code>. Dans une app multi-agents, chaque sandbox peut donc recevoir sa propre personnalité et ses propres limites, rédigées en langage naturel.
</Callout>
