Pas question de refaire à la main *Créer votre agent* → *Brancher le modèle* → *Identité et personnalité* pour chaque spécialiste. La fleet est donc décrite dans **un seul fichier de spécification** et lancée par **un seul script**, qui enchaîne en boucle la création de la sandbox, la restriction de la policy et le dépôt de la persona.

## La spécification : une ligne par agent

Le fichier `fleet.txt` décrit toute la fleet, à raison d'**un agent par ligne, sur trois colonnes séparées par des espaces** :

```text
# name      backend(host:port, or "-")                                              skill(@scope/name, or "-")
logs        logging-loki-gateway-http.openshift-logging.svc.cluster.local:8080      -
metrics     thanos-querier.openshift-monitoring.svc.cluster.local:9092              -
traces      tempo-tempostack-gateway.observability-hub.svc.cluster.local:8080       -
events      logging-loki-gateway-http.openshift-logging.svc.cluster.local:8080      -
analyst     -                                                                       -
```

Le rôle de chaque colonne :

- **`name`** : le nom de l'agent. C'est aussi le nom du dossier `manifests/openclaw/fleet-roles/<name>/`, qui contient ses fichiers `IDENTITY.md` et `SOUL.md`. La ligne `logs` donne ainsi une sandbox nommée `logs`, dotée de la persona définie dans `fleet-roles/logs/`.
- **`backend`** : l'**unique** `host:port` qu'autorisera la policy d'egress de l'agent (son seul outil). Il s'agit de la gateway du Loki Operator (`:8080`) pour l'agent logs, du **port multi-tenant `:9092`** de Thanos Querier pour metrics (ce port ne répond qu'aux requêtes limitées à un namespace, `?namespace=…`, et vérifie que l'appelant a le droit de lire ce namespace), de la gateway Tempo (`:8080`) pour traces, et de nouveau de la gateway Loki pour `events` (qui lit le flux d'events Kubernetes que votre propre event-exporter envoie dans Loki). Indiquez **`-`** pour *n'autoriser aucun egress* : c'est le cas d'`analyst`, qui se contente de raisonner sur ce que les autres ont trouvé.
- **`skill`** : un skill facultatif, issu du registry, à installer comme outil à part entière (par exemple un skill `@workshop/promql` qui fournit `promql(query)` au lieu d'appels `curl` écrits à la main). **`-`** signifie aucun skill : l'agent fonctionne quand même et interroge son backend en suivant les instructions de son `SOUL.md`. Pour en ajouter un, publiez-le comme dans la leçon *Skills et gouvernance*, puis inscrivez `@workshop/<name>` dans cette colonne.

<Callout type="note" title="Des colonnes séparées par des espaces, pas par des deux-points">
Le backend est lui-même de la forme <code>host:port</code> et contient donc un deux-points : les colonnes sont séparées par des <strong>espaces</strong>, et non par <code>:</code>. Alignez-les comme bon vous semble, <code>fleet.sh</code> lit les trois premiers champs. Les lignes qui commencent par <code>#</code> sont des commentaires.
</Callout>

## Le script `scripts/fleet.sh`

Pour chaque ligne, le script :

- crée une sandbox isolée (avec `--policy` et le provider d'inférence attaché) ;
- écrit une **policy limitée à ce seul backend**, plus le registry de skills interne au cluster (tout le reste reste en deny-by-default) ;
- dépose la persona de l'agent depuis `manifests/openclaw/fleet-roles/<name>/`, en y renseignant vos namespaces ;
- remet à l'agent un token de lecture de courte durée (24 h) pour les backends de télémétrie, valable uniquement sur **vos** namespaces.

Lancez la fleet : la commande crée les sandboxes, restreint chaque policy, dépose chaque persona et affiche sa progression agent par agent. Dans ce lab, la fleet a été créée à l'avance : chaque agent affiche `already Ready — re-staging files only`, et la commande se contente de rafraîchir ses fichiers, sa policy et son token de télémétrie :

```bash
./scripts/fleet.sh up fleet.txt
```

Suivez ensuite leur passage à l'état Ready (`status` s'appuie sur `openshell sandbox list`) :

```bash
./scripts/fleet.sh status
```

### Observer ce qui tourne

Affichez les **pods** des sandboxes dans le cluster (chaque agent est un pod isolé nommé `default--<agent>`, accompagné d'un pod `os-supervisor-…`) :

```bash
oc get pods -n "$OPENSHELL_NS"
```

La même fleet, vue sous forme de **ressources personnalisées Sandbox** : la gateway en crée une par agent, et le contrôleur agent-sandbox en dérive le pod correspondant :

```bash
oc get sandboxes -n "$OPENSHELL_NS"
```

Et la fleet **vue par la gateway** elle-même, avec la phase de chaque sandbox : `openshell` interroge la gateway, et non l'API Kubernetes :

```bash
openshell sandbox list
```

Examinez la **policy effective** d'un agent : elle prouve que son egress se limite à son outil.

```bash
openshell policy get metrics --full -o json
```

Suivez enfin la **piste d'audit** d'un agent, c'est-à-dire chaque décision d'egress le concernant, qu'elle l'autorise ou le bloque :

```bash
openshell logs metrics --source sandbox
```

Lorsque vous aurez **terminé l'atelier** et voudrez supprimer la fleet, utilisez la commande ci-dessous. *Ne la lancez pas maintenant* : elle supprime tout.

```bash-ref
./scripts/fleet.sh down fleet.txt
```

C'est la policy écrite pour chaque agent qui assure la gouvernance : elle est **propre à son outil**. En dehors du registry, l'agent `metrics` n'a droit *qu'à* ceci :

```yaml
network_policies:
  in-cluster-registry: { … }                 # every agent: install skills from your registry
  tool-egress:
    name: tool-egress
    endpoints: [ { host: thanos-querier.openshift-monitoring.svc.cluster.local, port: 9092, access: full } ]
    binaries: [ { path: /usr/bin/node }, { path: /usr/bin/curl } ]
```

`metrics` peut donc joindre Thanos Querier et rien d'autre ; `logs` et `events` n'ont accès qu'à la gateway Loki ; `analyst` n'a **aucun `tool-egress`**. Si un agent tente de joindre le backend d'un autre, le proxy refuse la connexion, et le refus apparaît dans l'onglet **Décisions de policy** de la page [Live](/learn/live).

## Un rôle par agent : les fichiers SOUL

Ce sont les fichiers `IDENTITY.md` et `SOUL.md`, déjà rencontrés dans *Identité et personnalité*, qui différencient le comportement des spécialistes. Chacun a les siens, que `fleet.sh` dépose depuis `manifests/openclaw/fleet-roles/<name>/`. En voici l'essentiel (les fichiers complets, avec leur chemin sur le disque, sont consultables sur la page [La fleet en un coup d'œil](/learn/fleet-status)) :

```markdown
# Scout 🔎 — logs/SOUL.md
Backend: Loki Operator gateway. Read the app's OWN log output in your demo namespace:
  {kubernetes_namespace_name="<demo ns>"} |= "error"  → the error lines and which pods are logging.

# Gauge 📈 — metrics/SOUL.md
Backend: Thanos Querier (tenancy port 9092, ?namespace=<demo ns>). Quantify it with RED metrics:
  sum by (code) (rate(shop_requests_total{namespace="<demo ns>"}[2m])) + the average latency. Numbers, not narratives.

# Trace 🧵 — traces/SOUL.md
Backend: Tempo gateway. Recent ERROR traces of the shop service in your namespace:
  { resource.service.name = "shop" && resource.k8s.namespace.name = "<demo ns>" && status = error } → WHERE it breaks.

# Probe 🛎️ — events/SOUL.md
Backend: Loki Operator gateway — but a DIFFERENT stream than Scout: the Kubernetes events your own event-exporter ships in,
  {kubernetes_namespace_name="<openshell ns>",kubernetes_container_name="event-exporter"} |= "reason"  → what CHANGED.

# Sage 🧠 — analyst/SOUL.md
NO egress, NO tools. Reason only over the others' findings → conclude the root cause + recommend the fix.
```

**`logs` et `events` partagent donc le backend Loki, mais n'y lisent pas la même chose** : Scout lit les
lignes de log *de l'application* (`{kubernetes_namespace_name="<demo ns>"}`), tandis que Probe lit le flux d'events *du cluster*
(la sortie du conteneur `event-exporter`), autrement dit ce que le control plane rapporte lui-même des changements.
`fleet.sh` renseigne vos namespaces (<code><Ns which="demo" /></code> et <code><Ns which="openshell" /></code>) dans les fichiers SOUL :
dans un lab partagé, la fleet de chaque participant n'enquête donc que sur **sa propre** application de démo.
**Une identité, une SOUL et une policy limitée à un outil : voilà un spécialiste**, et chaque ligne de ce qui le définit est lisible.

## Le skill `cluster-telemetry` : comment un agent isolé lit son backend

Les SOUL ci-dessus passent une difficulté sous silence : l'outil `web_fetch` intégré à OpenClaw **refuse
les adresses privées, internes ou du cluster** (une protection contre le SSRF). Or Loki, Prometheus et Tempo
sont tous exposés sur `*.svc.cluster.local` (des ClusterIP privées) : un agent isolé *ne peut donc pas*
les interroger avec `web_fetch`. C'est le rôle du **skill `cluster-telemetry`**, que `fleet.sh` dépose
dans chaque agent doté d'un backend, sous `/sandbox/.agents/skills/cluster-telemetry/` :

- **`SKILL.md`** indique à l'agent que son backend se trouve dans le cluster et qu'il ne doit donc pas
  utiliser `web_fetch`, mais ce skill, via l'outil `exec` : lancer UNE seule requête, puis rapporter les valeurs concrètes obtenues.
- **`tq.js`** est un petit script que l'agent lance avec `node …/tq.js '<url>'`. Il délègue l'appel à **`curl`**,
  un binaire autorisé en egress : la requête reste donc soumise à la policy de l'agent, limitée à un seul backend.
  **Rien n'est affaibli : la protection contre le SSRF reste active partout ailleurs.** Le script affiche ensuite
  un résumé *compact*, en quelques lignes. C'est important : renvoyer le JSON brut de la télémétrie à un petit modèle
  saturerait sa fenêtre de contexte. Il sait lire les vecteurs Prometheus, les flux Loki et les résultats de recherche Tempo,
  et présente les events Kubernetes de façon lisible (`[Warning] Failed: Failed to pull image … (Pod/shop-…)`).

Tous les agents accèdent ainsi à leur backend **de la même manière, sous contrôle** : avec `curl`, dans le cadre
de leur policy d'egress. Le skill complet (`SKILL.md` et un `tq.js` d'environ 140 lignes) se trouve dans `manifests/openclaw/skills/cluster-telemetry/`.

<Callout type="note" title="Deux sortes de skills à ne pas confondre">
Le skill <strong>cluster-telemetry</strong> décrit ci-dessus est déposé automatiquement dans chaque agent : c'est
<em>par lui</em> qu'ils lisent leur backend. La colonne <code>skill</code> de <code>fleet.txt</code> est un mécanisme
<em>distinct et facultatif</em> : elle permet d'installer depuis votre registry privé (partie V) un outil à part entière,
par exemple <code>@workshop/promql</code>, qui fournit un outil typé <code>promql(query)</code>. Elle vaut <code>-</code>
par défaut : cluster-telemetry et la SOUL suffisent au bon fonctionnement des agents.
</Callout>

<Callout type="note" title="Pourquoi la fleet peut grandir sans risque">
Pour ajouter un sixième agent, il suffit d'une ligne de plus dans <code>fleet.txt</code> et d'un dossier de persona. Le périmètre de confiance ne s'élargit pas pour autant : le nouvel agent n'accède qu'à un seul hôte supplémentaire, cette autorisation figure dans sa policy, et chacun de ses appels est consigné dans l'audit log.
</Callout>

Lancez la fleet, vérifiez avec `status` que tous les agents sont Ready, puis passez au chapitre suivant pour les mettre au travail.
