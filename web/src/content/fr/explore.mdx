Vous connaissez maintenant les composants. Avant de construire pour de bon, **prenez en main l'ensemble du control plane (plan de contrôle), comme le ferait un opérateur** : observer, gouverner, exposer, le tout avec la CLI `openshell`. Vous allez créer une **sandbox jetable**, uniquement pour expérimenter (ni OpenClaw ni modèle : ce sera l'objet de la partie IV). À la fin de ce chapitre, vous aurez utilisé chacune des fonctions d'OpenShell. Toutes les commandes s'exécutent dans le shell du lab, directement sur votre gateway.

Commencez par créer la sandbox jetable. `--from` désigne l'image de la sandbox : ici, l'image OpenClaw de version figée (`$OPENCLAW_SANDBOX_IMAGE`, déjà téléchargée sur les nœuds ; OpenClaw ne sera pas lancé dans cet exercice). `--policy` est obligatoire en pratique : sans policy, une sandbox n'atteint jamais l'état Ready. `--detach -- sleep infinity` fournit à la sandbox un processus principal qui la maintient en vie, et vous rend la main dès qu'elle a démarré (une commande qui se termine, comme `true`, laisserait la sandbox à l'état *Completed*). Enfin, `--no-tty` la lance en mode non interactif.

```bash
openshell sandbox create --name lab --no-tty \
  --from "$OPENCLAW_SANDBOX_IMAGE" \
  --policy ~/workshop/policies/openclaw-sandbox.yaml \
  --detach -- sleep infinity
```

Affichez la liste de vos sandboxes :

```bash
openshell sandbox list
```

## 1. Vérifier l'état de la gateway

```bash
openshell status
```

Si la commande affiche `Status: Connected` suivi d'un numéro de version, le control plane répond.

## 2. Inspecter une sandbox

```bash
openshell sandbox get lab
```

Repérez la **Phase**, la **Policy source** (propre à la sandbox ou globale à la gateway) et la **Revision**, incrémentée à chaque modification de la policy. La policy effective s'affiche à la suite.

## 3. La piste d'audit — `logs`

C'est la brique d'observabilité d'OpenShell : chaque action de la gateway et des sandboxes y est consignée sous forme structurée. Vous pouvez y suivre, étape par étape, la séquence de démarrage étudiée plus tôt :

```bash
openshell logs lab --source gateway
```

Vous y trouverez `Creating sandbox in Kubernetes` puis `issued generation-bound gateway sandbox JWT` : c'est l'émission de l'identité de la sandbox, la poignée de main décrite dans le chapitre d'architecture. Vous pouvez aussi filtrer les entrées :

```bash
openshell logs lab --source sandbox --level debug
```

Suivez maintenant le flux en direct. Cette commande **ne rend pas la main** : elle affiche les nouvelles entrées au fur et à mesure.

```bash
openshell logs lab --tail
```

Quand vous avez terminé, appuyez sur <kbd>Ctrl-C</kbd> dans le shell pour interrompre le suivi et récupérer l'invite de commande. Tant que vous ne le faites pas, la commande reste bloquée.

<Callout type="note" title="Un flux prêt pour votre SIEM">
Chaque entrée est un événement de sécurité au format OCSF. En production, ce flux alimente votre SIEM : chaque décision allow/deny, chaque changement de policy, chaque exécution de commande, avec la sandbox qui en est à l'origine.
</Callout>

## 4. Gouverner la sandbox — `policy`

Affichez la policy effective et son historique :

```bash
openshell policy get lab        # the policy currently in force
```

```bash
openshell policy list lab       # revision history, with a status per revision
```

Chaque modification de la policy crée une **révision**. Dans l'historique, le **Status** d'une révision reste à `Pending` tant que le supervisor de la sandbox n'a pas confirmé l'avoir chargée ; il passe alors à `Loaded`. La révision précédente devient `Superseded`, et une révision rejetée par le supervisor apparaît en `Failed`. `policy get` affiche toujours la policy *compilée et en vigueur à cet instant*. Comme le supervisor de notre sandbox `lab` est actif (son processus principal tourne toujours), vous verrez la première révision passer à `Loaded` en quelques secondes.

`openshell policy` propose aussi `set` et `update`, pour modifier les règles d'egress d'une sandbox en cours d'exécution (hot-reload, sans redémarrage ; `--wait` attend que le supervisor les ait chargées). Vous retrouvez là, en direct, la boucle audit → enforce décrite dans le chapitre sur les policies.

## 5. D'où vient la clé du modèle ? — `provider`

```bash
openshell provider list
```

Un **provider** est un identifiant conservé par la gateway (votre clé d'inférence, un token GitHub, etc.). Son type est défini par un **provider profile**, qui précise vers quel hôte il peut être envoyé et quels binaires ont le droit de l'envoyer. Lorsque vous associez un provider à une sandbox (`sandbox create --provider …` ou `openshell sandbox provider attach`), la sandbox ne voit qu'un **placeholder** : le supervisor le remplace par le vrai secret au moment où la requête sort vers l'hôte autorisé. Notre sandbox `lab` n'a aucun provider associé :

```bash
openshell sandbox provider list lab
```

C'est précisément ainsi que, dans la partie IV, vous donnerez accès à un modèle à votre agent, sans jamais lui confier la clé.

## 6. Exposer un port — `forward` / `service`

Si une sandbox expose un service HTTP, vous pouvez y accéder sans passer par `oc` :

```bash
openshell service list           # exposed sandbox services
openshell forward list           # active port-forwards
```

(Au chapitre « Ouvrir l'interface de l'agent », vous verrez `openshell forward` à l'œuvre : le sidecar `openclaw-forward` du pod workshop l'exécute déjà pour exposer la Control UI de votre agent.)
