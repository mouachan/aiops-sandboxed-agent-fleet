Le Helm chart a tout déployé sur un véritable **cluster OpenShift** : vous pouvez ainsi consacrer votre temps à l'agent plutôt qu'à l'infrastructure. Ce chapitre présente ce qui tourne sur le cluster et vous permet de l'explorer en direct.

## L'infrastructure sous-jacente

Le cluster repose sur **Red Hat OpenShift**, la distribution Kubernetes d'entreprise qui intègre notamment les Routes, les SecurityContextConstraints et la CLI `oc`. Le Helm chart y a installé la gateway OpenShell et ses dépendances ; vos agents s'y exécuteront sous forme de pods encadrés par des policies.

```text
OpenShift cluster
├── <openshell namespace>            ← gateway + registry + this workshop + your agent sandboxes
├── <demo namespace>                 ← the demo app (Part VI incident lab)
├── openshift-monitoring namespace   ← Prometheus (Thanos Querier), Alertmanager
├── openshift-logging namespace      ← LokiStack + ClusterLogForwarder (log aggregation)
├── observability-hub namespace      ← TempoStack, OTEL Collector, RustFS object storage (tracing)
└── monitoring namespace             ← Grafana (dashboards)
```

Vos deux namespaces sont <code><Ns which="openshell" /></code> et <code><Ns which="demo" /></code> (`openshell` et `demo` sur un cluster mono-utilisateur ; une paire par participant dans un lab partagé). Dans le shell du lab, ils correspondent aux variables `$OPENSHELL_NS` et `$DEMO_NS`.

## L'explorer en direct

Dans le shell du lab, `oc` est déjà connecté au cluster. Vérifiez que les nœuds sont opérationnels :

```bash
oc get nodes
```

Les nœuds à l'état `Ready` constituent votre cluster. Regardez maintenant ce qui a déjà été déployé pour vous :

```bash
oc get project "$OPENSHELL_NS" "$DEMO_NS"
oc -n "$OPENSHELL_NS" get pods
```

Votre namespace contient la **gateway** (`openshell-0`), en cours d'exécution : c'est le control plane des agents, utilisé dans toute la suite de l'atelier. S'y ajoutent le registry de skills et le pod workshop, qui sert ce site. Un pod d'agent comme `default--shifty` peut aussi apparaître s'il a déjà été créé ; sinon, c'est *vous* qui créerez le vôtre dans la **partie IV**.

Il s'agit bien d'OpenShift : vérifiez la présence d'API propres à OpenShift.

```bash
oc get scc --no-headers | head -5
oc api-resources | grep -iE "route.openshift.io|security.openshift.io" | head
```

`SecurityContextConstraints` et `route.openshift.io` sont des extensions d'OpenShift, absentes d'un cluster Kubernetes standard. C'est la couche Red Hat sur laquelle s'exécutent vos agents.

Affichez les Routes créées par le Helm chart dans votre namespace : c'est par elles que votre navigateur accède à ce site et à l'interface de votre agent.

```bash
oc get routes -n "$OPENSHELL_NS"
```

<Callout type="tip" title="Des Routes plutôt que des NodePorts">
Les Routes OpenShift attribuent à chaque service un vrai nom d'hôte, avec terminaison TLS, sans bricolage à base de port-forwarding. Ce site, la Control UI de votre agent et Grafana sont accessibles par l'URL de leur Route. La gateway OpenShell, elle, n'est volontairement <em>pas</em> exposée par une Route : elle n'est joignable que depuis l'intérieur du cluster.
</Callout>
