Votre sandbox est démarrée, mais elle est vide : aucun modèle n'est configuré et aucun agent ne tourne. OpenClaw lit sa configuration dans `~/.openclaw/openclaw.json` (dans la sandbox, `HOME` vaut `/sandbox`). Vous allez lui indiquer un modèle, puis démarrer la **gateway OpenClaw**, qui fournit la Control UI et le runtime de l'agent.

## 1. Préparer la configuration : le vrai endpoint, un placeholder pour la clé

OpenClaw s'adresse à votre **vrai** endpoint d'inférence (`$NEMOCLAW_INFERENCE_BASE_URL`), mais la clé d'API qu'il présente n'est qu'un **placeholder**. Lorsque vous avez attaché le provider (option `--provider`, dans la leçon précédente), la sandbox a reçu une variable d'environnement `OPENAI_API_KEY`. Sa valeur n'est pas votre clé : c'est une référence que le supervisor sait interpréter. Affichez-la depuis l'*intérieur* de la sandbox :

```bash
PH=$(openshell sandbox exec -n shifty -- sh -c 'printf %s "$OPENAI_API_KEY"')
echo "inside the sandbox, OPENAI_API_KEY=$PH"
```

Vous obtenez une valeur du type `openshell:resolve:env:v<revision>_OPENAI_API_KEY` : un placeholder, sans aucune utilité hors de cette sandbox. Remarquez le numéro de **révision**. La gateway émet un nouveau placeholder à chaque modification du provider (une rotation de clé, par exemple), et l'ancien finit par ne plus être résolu. C'est pourquoi nous ne le recopions pas dans la configuration d'OpenClaw : celle-ci contient `${OPENAI_API_KEY}`, qu'OpenClaw remplace à chaque démarrage par le placeholder en vigueur dans la sandbox.

La configuration est construite sur l'hôte, puis déposée **dans la sandbox**. L'agent étant confiné par Landlock, nous l'écrivons via `openshell sandbox exec`, en base64, car exec n'accepte pas d'arguments sur plusieurs lignes :

```bash
cd ~/workshop
set -a; . .env; set +a
PW="${OPENCLAW_GATEWAY_PASSWORD:-openclaw}"
PH=$(openshell sandbox exec -n shifty -- sh -c 'printf %s "$OPENAI_API_KEY"')
[ -n "$PH" ] || echo "WARNING: OPENAI_API_KEY is empty inside the sandbox — is the provider attached? (openshell sandbox provider list shifty)"
OC=$(jq -n --arg model "$NEMOCLAW_MODEL" --arg pw "$PW" --arg base "$NEMOCLAW_INFERENCE_BASE_URL" \
  --argjson cw "${NEMOCLAW_MODEL_CONTEXT_WINDOW:-65536}" '{
    gateway: { port:30789, auth:{password:$pw}, remote:{ url:"ws://127.0.0.1:30789", password:$pw },
               trustedProxies:["127.0.0.1/32"],
               controlUi:{ dangerouslyAllowHostHeaderOriginFallback:true } },
    update:  { checkOnStart:false },
    memory:  { search:{ enabled:false } },
    agents:  { defaults:{ model:{ primary:("custom/"+$model) } } },
    models:  { providers:{ custom:{ baseUrl:$base,
               apiKey:"${OPENAI_API_KEY}", api:"openai-completions",
               models:[{id:$model,name:$model,contextWindow:$cw,maxTokens:4096}] } } }
  }')
echo "$OC" | jq .   # <- see exactly what we're about to write
openshell sandbox exec -n shifty -- sh -c "mkdir -p /sandbox/.openclaw && echo $(printf '%s' "$OC" | base64 -w0) | base64 -d > /sandbox/.openclaw/openclaw.json"
openshell sandbox exec -n shifty -- openclaw config validate
```

La commande `echo "$OC" | jq .` affiche le fichier `openclaw.json` exact que vous déposez. Il ressemble à ceci :

```json
{
  "gateway": {
    "port": 30789, "auth": { "password": "<your gateway password>" },
    "remote": { "url": "ws://127.0.0.1:30789", "password": "<your gateway password>" },
    "trustedProxies": [ "127.0.0.1/32" ],
    "controlUi": { "dangerouslyAllowHostHeaderOriginFallback": true }
  },
  "update": { "checkOnStart": false },
  "memory": { "search": { "enabled": false } },
  "agents": { "defaults": { "model": { "primary": "custom/<your-model>" } } },
  "models": {
    "providers": {
      "custom": {
        "baseUrl": "https://<your-endpoint>/v1",
        "apiKey": "${OPENAI_API_KEY}",
        "api": "openai-completions",
        "models": [ { "id": "<your-model>", "name": "<your-model>", "contextWindow": 65536, "maxTokens": 4096 } ]
      }
    }
  }
}
```

Le message `Config valid` confirme qu'OpenClaw accepte la configuration. Quelques réglages méritent une explication :

- `update.checkOnStart` et `memory.search` désactivent la recherche de mises à jour d'OpenClaw et les embeddings OpenAI utilisés pour la recherche en mémoire. Ces deux fonctions appelleraient Internet : la policy deny-by-default les bloquerait, et chaque blocage apparaîtrait comme une demande d'accès sur la page **Approvals**.
- `trustedProxies` servira dans la leçon suivante. Votre navigateur accède à cette interface via `openshell forward`, qui se connecte depuis `127.0.0.1` et relaie les en-têtes Forwarded envoyés par le navigateur. OpenClaw n'accepte ces en-têtes que d'un proxy déclaré dans cette liste ; sinon, il répond `proxy_attribution_required`.
- `models.providers.custom.baseUrl` pointe vers votre **vrai** endpoint, et `apiKey` vaut `${OPENAI_API_KEY}` : au démarrage, OpenClaw y substitue le **placeholder** de la sandbox, jamais votre clé.

Lorsqu'OpenClaw (`node`) appelle votre endpoint, la requête sort par le proxy d'egress de la sandbox. Le supervisor repère le placeholder dans l'en-tête `Authorization` et le remplace par la vraie clé, car le provider profile autorise cet identifiant à partir vers *cet* hôte, depuis *ce* binaire. Partout ailleurs, le placeholder reste un simple placeholder.

Vous pouvez afficher la règle que le provider a ajoutée à la policy **effective** de la sandbox (votre fichier, complété par les entrées issues du provider) :

```bash
openshell policy get shifty --full | grep -B2 -A8 -i "$(echo "$NEMOCLAW_INFERENCE_BASE_URL" | sed -E 's#^[a-z]+://([^/:]+).*#\1#')"
```

<Callout type="note" title="Pourquoi passer par la gateway plutôt que par oc cp">
L'agent est isolé par <strong>Landlock</strong> : il ne peut écrire que dans <code>/sandbox</code>, <code>/tmp</code> et <code>/var/tmp</code> (les répertoires système comme <code>/usr</code> sont en lecture seule, et tout le reste lui est invisible). Un fichier copié dans <code>/workspace</code> lui resterait donc invisible. De toute façon, dans un lab partagé, <code>oc cp</code> et <code>oc exec</code> sur les pods renvoient Forbidden. Un fichier écrit via <code>openshell sandbox exec</code> arrive là où l'agent le voit réellement. L'isolation est la même partout.
</Callout>

## 2. Démarrer (ou redémarrer) la gateway OpenClaw

Jusqu'ici, la sandbox ne faisait **rien** : son processus principal est `sleep infinity`. Vous allez maintenant y lancer **OpenClaw** avec la configuration que vous venez d'écrire, sur le port `30789`, avec une authentification par mot de passe. La gateway écoute sur le réseau (bind LAN) pour pouvoir être exposée ensuite.

OpenClaw est lancé avec `setsid` : il s'exécute ainsi dans sa **propre session** et continue de tourner une fois la commande terminée (un simple processus en arrière-plan serait tué à la fermeture de la session `exec`). La commande commence par arrêter toute gateway déjà lancée, en la désignant par son nom de processus, `openclaw-gateway`. C'est donc aussi elle qui sert à **redémarrer** OpenClaw pour appliquer de futures modifications de configuration. Vous pouvez la relancer à tout moment :

```bash
openshell sandbox exec -n shifty -- sh -c \
  'cd /sandbox && pkill -f "^openclaw-gateway"; sleep 2; pkill -9 -f "^openclaw-gateway"; setsid nohup openclaw gateway run --port 30789 --bind lan --auth password --password '"${PW:-${OPENCLAW_GATEWAY_PASSWORD:-openclaw}}"' --allow-unconfigured >/sandbox/gateway.log 2>&1 < /dev/null & echo $! > gateway.pid; for i in $(seq 1 15); do sed "s/\x1b\[[0-9;]*m//g" /sandbox/gateway.log | grep -qE "\[gateway\] ready" && break; sleep 2; done; sed "s/\x1b\[[0-9;]*m//g" /sandbox/gateway.log | grep -E "\[gateway\] ready"'
```

<Callout type="note" title="Pourquoi l'arrêter par son nom plutôt qu'avec `gateway restart` ou un fichier PID ?">
Il <em>existe</em> bien une commande <code>openclaw gateway restart</code> (ainsi que <code>gateway stop</code>), mais ces commandes pilotent un <strong>service système installé</strong> (systemd ou launchd). Or cette sandbox est un conteneur minimal, sans système d'init : c'est donc nous qui lançons la gateway, au premier plan. Un fichier PID ne serait pas plus fiable. OpenClaw renomme son processus en <code>openclaw-gateway</code> et peut se relancer lui-même sous un <strong>nouveau PID</strong> (c'est le cas après l'installation d'un plugin) ; une seconde gateway refuse alors de démarrer sur le même répertoire d'état. La commande cible donc le début du nom du processus, avec <code>pkill -f "^openclaw-gateway"</code>, un motif qui ne correspond jamais au shell qui exécute la commande. Enfin, une gateway bloquée en plein redémarrage ignore un arrêt normal, d'où le <code>pkill -9</code> deux secondes plus tard.
</Callout>

La ligne à surveiller est **`[gateway] ready`** : la Control UI et la gateway WebSocket de votre agent sont en service sur le port `30789`, à l'intérieur de la sandbox isolée. Vous les exposerez avec `openshell forward` dans la leçon suivante.

<Callout type="note" title="Et le port 30791 ?">
Vous verrez aussi passer <code>Browser control listening on http://127.0.0.1:30791</code>. Il s'agit d'un service auxiliaire <em>distinct</em>, qu'OpenClaw démarre systématiquement pour l'automatisation du navigateur (le relais de l'extension Chrome). Il n'écoute <strong>que sur 127.0.0.1</strong>, dans la sandbox, et n'est donc jamais exposé. Ignorez-le : votre gateway est celle du port <code>:30789</code>. Les lignes <code>security warning</code>, <code>update available</code> et <code>Chrome extension relay</code> sont, elles aussi, de simples avertissements sans conséquence.
</Callout>

## 3. Vérifier que le modèle répond

Demandez à l'agent d'exécuter un tour de conversation. C'est la gateway OpenClaw que vous venez de démarrer qui détient l'état de l'agent : la requête passe donc **par elle** (la CLI la trouve grâce à `gateway.port`, soit 30789). L'agent envoie alors son raisonnement à votre endpoint, avec le placeholder en guise de clé :

```bash
openshell sandbox exec -n shifty -- sh -c 'cd /sandbox && openclaw agent --agent main -m "Reply with exactly: PONG" --session-id smoke'
```

Vous devez obtenir `PONG`. Si l'agent répond, toute la chaîne fonctionne : il a joint le modèle **sans jamais détenir votre clé**.

<Callout type="note" title="Pourquoi ne pas utiliser --local">
<code>openclaw agent --local</code> exécute l'agent en mode embarqué, mais OpenClaw refuse ce mode tant qu'une gateway détient le même répertoire d'état (<em>« A Gateway is running for this state directory … Run without --local »</em>). Sans <code>--local</code>, la CLI s'adresse à la gateway déclarée dans <code>gateway.port</code> : c'est pour cela que la configuration fixe <code>port: 30789</code> (la valeur par défaut est 18789). Les agents de la fleet, dans la partie VI, ne font tourner aucune gateway : eux utilisent bien <code>--local</code>.
</Callout>

<Callout type="rh" title="La frontière de confidentialité, concrètement">
Voici le trajet de cette réponse : l'agent (<code>node</code>, qui ne détient que le placeholder) → le proxy d'egress de la sandbox → le supervisor, qui vérifie la policy effective (votre endpoint, autorisé pour <code>node</code> par le provider profile) et remplace le placeholder par votre vraie clé → votre endpoint d'inférence → retour. L'agent n'a jamais vu la clé, et celle-ci ne peut atteindre que l'hôte désigné dans le profile. Prochaine étape : ouvrir l'interface dans votre navigateur.
</Callout>
