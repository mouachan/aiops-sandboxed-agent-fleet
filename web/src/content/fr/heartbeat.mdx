Jusqu'ici, votre agent n'agit que lorsque **vous** lui parlez. Un **heartbeat** lui permet d'agir de lui-même : à intervalle régulier, la gateway le réveille avec un prompt de votre choix ; il effectue un tour, puis se rendort. C'est ce qui distingue un chatbot d'un *opérateur* : un agent qui veille pendant que vous êtes occupé ailleurs.

## Le principe

Un heartbeat est un **prompt planifié, comparable à une tâche cron**. À chaque intervalle (**30 minutes** par défaut), la gateway OpenClaw lance un tour de l'agent avec un prompt du type *« Run your checklist. Reply `HEARTBEAT_OK` if all is well, or raise an alert. »* L'agent fait son travail (vérifier un service, résumer les nouveautés, ranger son workspace) ; le résultat est journalisé et peut vous être notifié. Comme il s'agit d'un tour normal, il reste **entièrement gouverné** : pendant un heartbeat, l'agent ne peut joindre que les hôtes autorisés par votre policy d'egress.

<Callout type="note" title="Heartbeat ou cron ?">
OpenClaw propose aussi des <strong>automations</strong> (<code>openclaw automations</code>, alias <code>cron</code>) : des tâches dotées de leur propre planification, qui réveillent l'agent avec un message précis. Le <strong>heartbeat</strong>, lui, est géré par le système : un point régulier et ouvert, guidé par votre checklist. Choisissez une automation pour une tâche récurrente bien définie, et un heartbeat pour une surveillance générale.
</Callout>

## 1. Rédiger la checklist — `HEARTBEAT.md`

Comme `SOUL.md` et `IDENTITY.md`, la checklist est un fichier du workspace. Le prompt de réveil que vous définirez à l'étape 2 demande à l'agent de la relire à chaque battement (OpenClaw 2026.8 ne charge pas `HEARTBEAT.md` de lui-même). Créez un `HEARTBEAT.md` dans le workspace de l'agent :

```bash
openshell sandbox exec -n shifty -- sh -c 'printf "%s\n" "# Heartbeat checklist" "" "Every beat, do the following and keep it short:" "1. Note the current time and that you are alive." "2. If you have pending tasks in NOTES.md, summarise their status." "3. If everything is nominal, reply with exactly: HEARTBEAT_OK" "4. If something needs my attention, start your reply with: ALERT —" > /sandbox/.openclaw/workspace/HEARTBEAT.md'
```

<Callout type="note" title="Pourquoi printf plutôt qu'un heredoc">
<code>openshell sandbox exec -- sh -c '…'</code> refuse un argument entre guillemets qui contient de vrais sauts de ligne : un heredoc <code>cat &lt;&lt;EOF</code> échoue donc. <code>printf "%s\n" …</code> écrit un fichier de plusieurs lignes à partir d'une <strong>seule ligne</strong> de commande (c'est printf qui interprète les <code>\n</code> : aucun vrai saut de ligne n'est transmis).
</Callout>

## 2. Activer le heartbeat

Le heartbeat se configure sous `agents.defaults.heartbeat`, dans `openclaw.json`. Définissez l'intervalle, le prompt de réveil, le contexte d'exécution et la destination de la réponse. La commande ci-dessous appelle `openclaw config set` pour chaque clé ; vous **redémarrerez ensuite la gateway** pour qu'elle les prenne en compte :

```bash
openshell sandbox exec -n shifty -- sh -c 'openclaw config set agents.defaults.heartbeat.every 1m; openclaw config set agents.defaults.heartbeat.prompt "Read HEARTBEAT.md and run the checklist."; openclaw config set agents.defaults.heartbeat.isolatedSession true; openclaw config set agents.defaults.heartbeat.lightContext true; openclaw config set agents.defaults.heartbeat.target none; openclaw config get agents.defaults.heartbeat'
```

- **`every`** — l'intervalle (`1m`, `15m`, `30m`, `1h`…). Nous le réglons ici sur **`1m`** pour que vous puissiez voir un battement à l'étape suivante sans attendre une demi-heure ; en production, la valeur par défaut est `30m`. Le premier battement a lieu un intervalle *après* le redémarrage de la gateway, et non au démarrage (le log indique seulement `[heartbeat] started`) : comptez environ 1 minute avec `1m`, 30 minutes avec `30m`. Repassez à `30m` une fois le battement observé (voir plus bas).
- **`prompt`** — le message de réveil. Il doit renvoyer à votre `HEARTBEAT.md`.
- **`isolatedSession`** — exécute chaque battement dans une **session distincte**, pour ne pas encombrer l'historique de vos conversations.
- **`lightContext`** — charge un contexte réduit (moins de tokens consommés), car un heartbeat n'a généralement pas besoin de tout l'historique.
- **`target`** — la destination de la réponse. Avec `none`, elle reste interne. La valeur par défaut (`owner`) exige un canal de chat où envoyer la réponse ; cette sandbox n'en a aucun : sans `target none`, chaque battement planifié est donc ignoré avant même que l'agent ne démarre.

Vous pouvez aussi limiter le heartbeat aux heures de bureau avec **`activeHours`** (un objet avec `start`, `end` et, en option, `timezone` ; par exemple, des battements uniquement de 9 h à 18 h), pour qu'un agent de démo ne consomme pas de tokens toute la nuit.

Redémarrez la gateway pour appliquer ces réglages (même commande que dans *Brancher le modèle*) :

```bash
openshell sandbox exec -n shifty -- sh -c \
  'cd /sandbox && pkill -f "^openclaw-gateway"; sleep 2; pkill -9 -f "^openclaw-gateway"; setsid nohup openclaw gateway run --port 30789 --bind lan --auth password --password '"${OPENCLAW_GATEWAY_PASSWORD:-openclaw}"' --allow-unconfigured >/sandbox/gateway.log 2>&1 < /dev/null & echo $! > gateway.pid; for i in $(seq 1 15); do sed "s/\x1b\[[0-9;]*m//g" /sandbox/gateway.log | grep -qE "\[gateway\] ready" && break; sleep 2; done; sed "s/\x1b\[[0-9;]*m//g" /sandbox/gateway.log | grep -E "\[gateway\] ready|heartbeat" | tail -3'
```

## 3. Observer un battement

Le premier battement a lieu un intervalle (ici, environ une minute) **après** le redémarrage de la gateway. Cette commande interroge donc la gateway toutes les 10 secondes pour obtenir le dernier battement, jusqu'à ce qu'il apparaisse (2 minutes au maximum). Un battement comporte `"reason": "interval"` et un `status` : `ok-empty` signifie que l'agent a déroulé la checklist sans rien avoir à signaler ; si l'agent a quelque chose à dire, le battement contient sa réponse :

```bash
for i in $(seq 1 12); do b=$(openshell sandbox exec -n shifty -- openclaw system heartbeat last --json 2>/dev/null); case "$b" in *'"reason"'*) break ;; esac; echo "no beat yet, waiting…"; sleep 10; done; echo "$b"
```

Chaque battement est aussi un tour audité : il apparaît dans `openshell logs shifty`, comme toute autre action de l'agent.

**Ne sautez pas cette étape.** Une fois le battement observé, choisissez un rythme plus raisonnable : avec `1m`, votre agent sollicite le modèle toutes les minutes, toute la journée, alors que ce modèle est partagé par toute la salle. (Vous pouvez aussi limiter le heartbeat aux heures de bureau.) La gateway applique les réglages du heartbeat par hot-reload (rechargement à chaud), sans redémarrage :

```bash
openshell sandbox exec -n shifty -- sh -c 'openclaw config set agents.defaults.heartbeat.every 30m; openclaw config set agents.defaults.heartbeat.activeHours "{\"start\":\"09:00\",\"end\":\"18:00\"}" --strict-json'
```

<Callout type="rh" title="De l'assistant à l'opérateur">
Grâce au heartbeat, un modèle enfermé dans une sandbox devient un agent qui <strong>fonctionne en continu</strong> : il surveille, vérifie et rend compte de lui-même, toujours dans la même isolation deny-by-default. La fleet de la partie VI ne s'en sert pas (ses agents exécutent des tours ponctuels, sans gateway), mais c'est avec un heartbeat que vous garderiez un agent en veille entre deux incidents.
</Callout>
