Vous avez créé `shifty` avec `openshell sandbox create`. Chaque sandbox donne lieu à un **pod**, mais un pod *isolé*. Pour exécuter des commandes de l'*agent*, il faut entrer **dans la sandbox**, et il existe pour cela deux chemins qui ne mènent pas au même endroit. Comprendre cette différence, c'est comprendre OpenShell.

## Une sandbox, c'est un pod

```bash
oc -n "$OPENSHELL_NS" get pod default--shifty -o wide
```

C'est un pod ordinaire, nommé `default--shifty` (la gateway ajoute le workspace en préfixe), qui contient un conteneur `agent`. Son supervisor s'exécute dans un pod associé, `os-supervisor-…`. Dans ce conteneur, l'agent OpenClaw tourne au sein du **runtime de sandbox OpenShell** : un système de fichiers restreint par Landlock, et des connexions réseau systématiquement confrontées à la policy avant de sortir.

## Deux façons d'entrer

**`oc exec`** vous place directement dans le conteneur `agent`, sans passer par la gateway : rien de ce que vous y faites n'est contrôlé par la policy ni consigné dans l'audit log.

```bash
oc -n "$OPENSHELL_NS" exec default--shifty -c agent -- sh -c 'echo HTTPS_PROXY="$HTTPS_PROXY"; ls /sandbox >/dev/null 2>&1 && echo "can see /sandbox" || echo "no /sandbox here"'
```

<Callout type="warn" title="Lab partagé : cette commande renvoie Forbidden">
Dans un lab multi-utilisateurs, votre ServiceAccount n'est <strong>pas autorisé</strong> à lancer <code>oc exec</code> dans les pods des sandboxes : la commande ci-dessus renvoie <code>Forbidden</code> (<code>cannot create resource "pods/exec"</code>). C'est le RBAC qui joue son rôle : un exec direct contournerait la gateway, sa piste d'audit et l'isolation de la sandbox. Utilisez plutôt <code>openshell sandbox exec</code>, présenté ci-dessous : cette commande passe par la gateway et vous place à l'intérieur de l'isolation. Sur un cluster mono-utilisateur, <code>oc exec</code> fonctionne et vous montre le shell extérieur.
</Callout>

**`openshell sandbox exec`**, lui, vous place dans le contexte isolé de l'*agent* : le système de fichiers Landlock (`/sandbox`, `/tmp`) et le proxy d'egress contrôlé. C'est là que l'agent s'exécute réellement :

```bash
openshell sandbox exec -n shifty -- sh -c 'echo HTTPS_PROXY="$HTTPS_PROXY"; whoami; pwd'
```

Remarquez qu'**aucun** des deux shells ne définit `HTTPS_PROXY` : dans OpenShell 0.1.x, l'egress est intercepté de façon transparente. Chaque connexion ouverte par l'agent est confrontée à sa policy (binaire, hôte et port, puis requête HTTP) et journalisée : `openshell logs shifty --source sandbox` affiche par exemple des lignes `NET:OPEN … ALLOWED … [policy:websearch]`, et tout ce qui n'est pas autorisé est refusé. Le shell ouvert par `oc exec` échappe à ce circuit : aucune décision de policy, aucune trace d'audit. *Toute* l'isolation tient dans cette différence.

## Lancer la CLI de l'agent

Le binaire `openclaw` se trouve dans la sandbox. Exécutez-le en passant par la gateway, dans le contexte isolé :

```bash
openshell sandbox exec -n shifty -- openclaw --help
openshell sandbox exec -n shifty -- openclaw config get gateway
```

<Callout type="tip" title="À retenir">
<strong>OpenShell</strong> pilote les sandboxes depuis l'extérieur (c'est le control plane : <code>openshell …</code> ou <code>oc</code>). <strong>Dans une sandbox</strong>, vous lancez les commandes de l'agent lui-même avec <code>openshell sandbox exec -n shifty -- openclaw …</code>. Réservez <code>oc exec</code> au shell extérieur du pod : il contourne les contrôles de policy et la piste d'audit de la gateway, et ne vous montre donc pas le monde tel que l'agent le voit.
</Callout>

<Callout type="rh" title="Pourquoi cette isolation est essentielle">
C'est cette même isolation qui empêche une sandbox de la gateway d'atteindre l'API Kubernetes du cluster : l'agent ne sort que par le proxy contrôlé. Vous pouvez inspecter le pod de l'extérieur autant que vous le souhaitez ; l'agent, lui, reste confiné. C'est ce qui vous permet d'exécuter sans risque des agents auxquels vous ne faites pas confiance.
</Callout>
