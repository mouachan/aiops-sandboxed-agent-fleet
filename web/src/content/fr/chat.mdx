Votre navigateur est appairé et votre agent est branché sur un modèle. Il est temps de lui parler, tout en observant la plateforme que vous avez construite travailler en coulisses.

## Premier échange

Dans la Control UI d'OpenClaw (l'onglet ouvert au chapitre « Ouvrir l'interface de l'agent »), saisissez dans la zone de chat :

> Hi! Who are you, and what cluster are you running on?

L'agent répond en s'appuyant sur son **identité** (les fichiers `.md` du workspace, que vous modifierez au chapitre « Identité et personnalité »), avec le modèle que vous avez configuré. Chaque réponse implique un aller-retour vers votre endpoint d'inférence : la requête sort par le proxy d'egress de la sandbox, où le supervisor remplace le placeholder `OPENAI_API_KEY` par votre vraie clé, en direction du seul hôte autorisé par le provider.

## L'observer depuis le shell

Pendant la conversation, affichez la fin du log de la gateway de l'agent : vous y verrez en temps réel les tours de conversation, les tool calls et les requêtes envoyées au modèle.

```bash
openshell sandbox exec -n shifty -- sh -c 'tail -n 20 /sandbox/gateway.log'
```

Vérifiez aussi ce que l'agent a le droit de joindre, c'est-à-dire la policy deny-by-default en vigueur :

```bash
openshell policy get shifty --full
```

Tout ce que l'agent peut atteindre sur le réseau figure dans cette sortie. Demandez-lui de récupérer un site web quelconque : il en est tout simplement incapable, car cet egress n'est pas prévu dans la policy. Vous avez ainsi la garantie que l'agent fait ce que vous lui demandez, et *uniquement* ce que vous avez autorisé.

## Lui confier une vraie tâche

Donnez-lui un travail concret (il dispose d'un shell et d'outils dans sa sandbox) :

> Use your write tool to create the file /sandbox/haiku.txt containing a haiku about Kubernetes. Then use your read tool to read /sandbox/haiku.txt back to me.

Vous préférez le terminal ? Envoyez la même tâche par la gateway de l'agent :

```bash
openshell sandbox exec -n shifty -- sh -c 'cd /sandbox && openclaw agent --agent main --session-id haiku -m "Use your write tool to create the file /sandbox/haiku.txt containing a haiku about Kubernetes. Then use your read tool to read /sandbox/haiku.txt back to me."'
```

Vérifiez ensuite, depuis l'extérieur, que le fichier a bien été écrit dans son espace isolé :

```bash
openshell sandbox exec -n shifty -- cat /sandbox/haiku.txt
```

Si `cat` renvoie *No such file*, le modèle a répondu dans le chat sans appeler son outil write, ce qui arrive parfois avec les petits modèles. Renvoyez la tâche : c'est en nommant explicitement l'outil (« use your write tool ») que vous obtenez un résultat fiable.

L'agent a agi dans sa sandbox, et vous l'avez observé depuis le control plane (plan de contrôle). Tout l'intérêt est là : l'agent travaille dans un espace isolé, et c'est vous qui gardez les clés.

<Callout type="tip" title="Si une réponse n'arrive pas">
Vérifiez la configuration du modèle et l'autorisation de l'egress : <code>openshell sandbox exec -n shifty -- openclaw config get models.providers.custom</code> et <code>openshell logs shifty --tail</code>. Une requête bloquée apparaît comme un egress refusé dans l'audit log : ce n'est pas un bug, c'est la policy qui fait son travail.
</Callout>

<Callout type="rh" title="Votre agent est opérationnel">
Créé par la gateway, isolé, soumis à une policy, branché sur un modèle et accessible dans votre navigateur : vous l'avez entièrement mis en place vous-même, sur un vrai cluster OpenShift. Il ne vous reste plus qu'à vous l'<em>approprier</em> : identité, personnalité, et le control plane qui le fait tourner.
</Callout>
