Voici les pièges que nous avons rencontrés, pour vous éviter d'y tomber à votre tour. Le Helm chart en gère la plupart ; si quelque chose ne fonctionne pas, voici les points à vérifier (lancez les commandes dans le shell).

## L'interface de l'agent ne répond pas sur :30789
L'interface de l'agent est rendue accessible hors de la sandbox isolée par `openshell forward`, que le sidecar `openclaw-forward` du pod workshop exécute (votre shell partage son réseau). Vérifiez le tunnel, ainsi que le bon fonctionnement de la gateway OpenClaw dans la sandbox :

```bash
curl -s -o /dev/null -w "OpenClaw UI: HTTP %{http_code}\n" http://127.0.0.1:30789/
openshell sandbox exec -n shifty -- sh -c 'tail -3 /sandbox/gateway.log'   # gateway listening?
```

## La gateway est injoignable
La gateway est exposée par un Service interne au cluster, dans votre namespace (sans Route publique). Vérifiez que le Service existe, que le pod de la gateway tourne et que la CLI pointe bien vers elle :

```bash
oc -n "$OPENSHELL_NS" get svc openshell
oc -n "$OPENSHELL_NS" get pods
openshell gateway list
openshell status
openshell sandbox list
```

Si le pod tourne mais que la gateway ne répond pas, consultez ses logs :

```bash
oc -n "$OPENSHELL_NS" logs openshell-0 --tail=50
```

## Une sandbox n'atteint jamais l'état Ready (ou passe à Completed)
Deux causes classiques : la sandbox a été créée **sans `--policy`** (son supervisor attend alors indéfiniment une policy dont la gateway ne dispose pas), ou sa commande principale **s'est terminée** (par exemple `-- true`), ce qui la laisse à l'état *Completed*. Examinez-la, puis recréez-la correctement :

```bash
openshell sandbox list
oc -n "$OPENSHELL_NS" get sandboxes,pods
```

```bash-ref
openshell sandbox delete shifty
openshell sandbox create --name shifty --from "$OPENCLAW_SANDBOX_IMAGE" \
  --policy ~/workshop/policies/openclaw-sandbox.yaml \
  --provider "$NEMOCLAW_INFERENCE_PROVIDER" --no-tty --detach -- sleep infinity
```

## L'agent reçoit une erreur 401 ou n'atteint pas le modèle
L'agent ne peut joindre votre endpoint que par l'intermédiaire d'un **provider associé** à sa sandbox. Vérifiez cette association, puis le provider lui-même :

```bash
openshell sandbox provider list shifty
openshell provider list
```

Si aucun provider n'est associé, associez-le et attendez que la sandbox ait pris en compte le changement, puis redémarrez OpenClaw (seuls les *nouveaux* processus reçoivent le placeholder de l'identifiant) :

```bash-ref
openshell sandbox provider attach shifty "$NEMOCLAW_INFERENCE_PROVIDER" --wait
```

## La console OpenShift est injoignable
Vérifiez la Route et les pods de la console (dans un lab partagé, la console n'est pas toujours proposée ; le site de l'atelier masque alors son lien) :

```bash
oc -n openshift-console get route
oc -n openshift-console get pods
```

## OpenClaw demande d'appairer l'appareil (device pairing)
C'est normal : approuvez la demande (voir [Appairer votre navigateur](/learn/pairing), dans la partie IV) :

```bash
approve-browser
```

## Le téléchargement des images se bloque (« unexpected EOF »)
Vérifiez la connectivité réseau du cluster : il s'agit souvent d'un problème de MTU ou de DNS sur l'infrastructure sous-jacente.

<Callout type="note" title="Le Helm chart peut être redéployé">
Le Helm chart est idempotent : corrigez la cause du problème, puis redéployez-le pour rétablir l'état attendu.
</Callout>
