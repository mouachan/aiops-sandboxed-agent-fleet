Avant de lancer la moindre commande d'agent, il faut comprendre la couche qui *gère* l'agent : **OpenShell**, le control plane (plan de contrôle) des sandboxes. Dans cette leçon, vous n'utilisez que de simples commandes `oc` sur le cluster ; aucun agent n'entre encore en jeu.

## La gateway OpenShell

OpenShell est déployé sous forme de StatefulSet. Affichez-le :

```bash
oc -n "$OPENSHELL_NS" get statefulset,pods,svc
```

Son **compute driver Kubernetes** surveille en permanence les sandboxes. Une gateway en bonne santé le consigne dans ses logs, à quelques secondes d'intervalle :

```bash
oc -n "$OPENSHELL_NS" logs openshell-0 | grep -i "Listing sandboxes" | tail -3
```

Si vous voyez `Listing sandboxes from Kubernetes`, le control plane est opérationnel et surveille les sandboxes.

## L'API des sandboxes : un CRD

Une « sandbox » est une ressource personnalisée Kubernetes, `sandboxes.agents.x-k8s.io`. C'est sous cette forme que la plateforme représente l'environnement isolé d'un agent :

```bash
oc get crd sandboxes.agents.x-k8s.io
```

### Lister les sandboxes

Listez les sandboxes de votre namespace (la gateway les crée dans son propre namespace) :

```bash
oc get sandboxes -n "$OPENSHELL_NS"
```

Dans ce lab, vous voyez déjà les cinq agents de la fleet de la partie VI (`default--logs`, `default--metrics`, …). Votre propre agent apparaîtra dans cette liste une fois créé, dans la partie IV, sous le nom `default--shifty` (la gateway ajoute le nom du workspace en préfixe). Ce qui compte, c'est la *forme* : chaque agent créé par la gateway se présente ici comme un CR `Sandbox` (`agents.x-k8s.io/v1beta1`), que vous pouvez inspecter avec un simple `oc` (`oc -n "$OPENSHELL_NS" describe sandbox default--<name>`). L'API se résume à cela : un objet Kubernetes.

## Policies : ce qu'une sandbox a le droit de faire

La policy d'une sandbox gérée par OpenShell tient dans **un seul fichier YAML, en deux parties** : une section réseau *dynamique*, qui accepte le hot-reload (rechargement à chaud) sur une sandbox en cours d'exécution, et des sections *statiques* (système de fichiers et processus), figées à la création et appliquées par le noyau. Cliquez sur chaque partie pour l'explorer :

<PolicyExplorer />

Pour les sandboxes créées par la gateway OpenShell, chaque section correspond à un mécanisme d'application réel ; rien n'est purement indicatif :

| Couche | Protège contre | Appliquée par | Modifiable à chaud ? |
| --- | --- | --- | --- |
| `network_policies` | egress non autorisé, exfiltration de données | proxy CONNECT + OPA, par binaire | ✅ hot-reload |
| `filesystem` | altération des binaires, vol d'identifiants | **Landlock LSM** (noyau) | ❌ recréer la sandbox |
| `process` | élévation de privilèges, fork bombs, appels système interdits | **seccomp-BPF** + abandon des privilèges | ❌ recréer la sandbox |

### Sur votre cluster

Le dépôt contient la policy OpenShell que votre agent utilisera. Affichez le fichier :

```bash
cat ~/workshop/policies/openclaw-sandbox.yaml
```

Il est court. Le voici en entier ; chaque ligne est un guardrail (garde-fou) :

```yaml
version: 1

filesystem_policy:                       # what the agent may touch on disk
  include_workdir: true
  read_only:  [/usr, /lib, /proc, /dev/urandom, /app, /etc, /var/log]
  read_write: [/sandbox, /tmp, /var/tmp, /dev/null]

landlock:
  compatibility: best_effort             # enforce the FS rules via the kernel (Landlock LSM)

process:
  run_as_user: sandbox                   # the agent runs unprivileged, never root
  run_as_group: sandbox

network_policies:                        # a MAP of named egress rules — deny-by-default
  in-cluster-registry:                   # the workshop's private npm registry (skills)
    name: in-cluster-registry
    endpoints:
      - { host: registry.openshell.svc.cluster.local, port: 4873, access: full, protocol: rest, allow_encoded_slash: true }
    binaries:
      - { path: /usr/bin/node }          # ONLY node/npm may use this rule
      - { path: /usr/local/bin/node }
      - { path: /usr/bin/npm }
      - { path: /usr/local/bin/npm }
  npm-registry:                          # public npm, for plugin dependencies
    name: npm-registry
    endpoints:
      - { host: registry.npmjs.org, port: 443, access: full, protocol: rest, allow_encoded_slash: true }
    binaries: [ { path: /usr/bin/node }, { path: /usr/local/bin/node }, { path: /usr/bin/npm }, { path: /usr/local/bin/npm } ]
  websearch:                             # DuckDuckGo, for the web-search tool
    name: websearch
    endpoints:
      - { host: duckduckgo.com, port: 443, access: full }
      - { host: html.duckduckgo.com, port: 443, access: full }
      - { host: lite.duckduckgo.com, port: 443, access: full }
    binaries: [ { path: /usr/bin/node }, { path: /usr/local/bin/node } ]
```

Reprenons-le bloc par bloc :

- **`version`** — la version du schéma de policy, ici simplement `1`.
- **`filesystem_policy`** — ce que l'agent voit du disque. `read_only` couvre les répertoires système (l'agent ne peut donc modifier ni les binaires ni les fichiers de configuration) ; `read_write` se limite **strictement** à son répertoire personnel (`/sandbox`), à `/tmp`, `/var/tmp` et `/dev/null`. Tout ce qui ne figure pas dans la liste, comme `/workspace` ou le système de fichiers de l'hôte, n'existe tout simplement pas pour lui.
- **`landlock`** — ces règles ne sont pas de simples recommandations : elles sont appliquées par **Landlock**, un module de sécurité du noyau Linux. Même un agent compromis ne peut pas s'en affranchir.
- **`process`** — l'agent s'exécute sous l'utilisateur non privilégié `sandbox`, jamais en root (ce que renforcent seccomp-BPF et l'abandon des privilèges).
- **`network_policies`** — le cœur de la policy : une **map** de règles nommées, en deny-by-default. Chaque règle associe des **endpoints** (l'hôte et le port que l'agent peut joindre) à des **binaires** (les exécutables autorisés à emprunter cette sortie). Ici, trois règles : le registry de skills interne au cluster, le registry npm public et DuckDuckGo, toutes réservées à `node`/`npm`, et à eux seuls. (Dans un lab partagé, le nom d'hôte du registry contient votre propre namespace, <code>registry.<Ns which="openshell" />.svc.cluster.local</code> ; le workshop le réécrit au démarrage.)

Autrement dit : *« `node` peut ouvrir une connexion sur `:443` vers `duckduckgo.com`, `curl` ne le peut pas, et personne ne peut aller ailleurs. »* C'est ce contrôle de l'egress **par binaire et par hôte** qui empêche un agent victime d'une prompt injection d'exfiltrer des données par un canal détourné. En somme, un pare-feu qui bloque tout, percé de quelques portes étroites et bien identifiées.

<Callout type="note" title="Et l'endpoint du modèle ?">
Notez que la policy ne contient <strong>aucune règle pour l'inférence</strong>. Cet accès est fourni par un <em>provider</em> attaché à la sandbox (voir la dernière section) : son provider profile ajoute l'endpoint d'inférence à la policy <em>effective</em> de la sandbox, pour les seuls binaires listés, et se charge de la clé. Sans provider attaché, un appel vers l'hôte d'inférence est refusé, comme tout le reste.
</Callout>

Vous verrez cette même policy **appliquée en direct** dans la leçon suivante, sur une sandbox jetable, puis à nouveau en construisant votre agent dans la partie IV. `openshell policy get <name>` affiche la policy *effective* (ajoutez `--full` pour y inclure les règles apportées par les providers). La gateway traduit ce fichier en règles appliquées par le noyau (Landlock/seccomp) et par le proxy (egress filtré par OPA).

<Callout type="tip" title="Affiner la policy par itérations">
Pour une sandbox créée par la gateway, commencez en mode <strong>audit</strong> (les violations sont journalisées mais pas bloquées) et repérez les refus dans <code>openshell logs &lt;name&gt;</code>. Ajoutez à <code>network_policies</code> les endpoints dont vous avez réellement besoin, puis passez en mode <strong>enforce</strong>. Comme les règles réseau sont prises en compte par hot-reload, vous durcissez la policy sans interruption de service.
</Callout>

<Callout type="note" title="Qui réconcilie la sandbox ?">
Le <strong>contrôleur</strong> agent-sandbox (kubernetes-sigs/agent-sandbox v1.0.3, installé une seule fois par cluster) transforme le CR <code>Sandbox</code> en pod, dans le respect du RBAC et des Security Context Constraints du namespace. Les sandboxes s'exécutent sous la SCC par défaut <code>restricted-v2</code>, sans aucun privilège supplémentaire. OpenShell constitue le control plane au sens large : la gateway, plus un <strong>supervisor</strong> par sandbox (un pod <code>os-supervisor-…</code> accompagne chacune d'elles).
</Callout>

## Identifiants : providers et placeholders

C'est aussi la gateway qui conserve les secrets, sous la forme de deux objets du control plane que vous utiliserez dans la partie IV :

- Le **provider profile** — le contrat d'accès d'un type d'identifiant : vers quels **hôte et port** il peut être envoyé, sous quelle forme (par exemple `Authorization: Bearer`), quelle variable d'environnement le porte dans la sandbox (`OPENAI_API_KEY`) et quels **binaires** ont le droit de l'envoyer. Il ne contient aucun secret.
- Le **provider** — une instance de ce profile, qui détient l'**identifiant** proprement dit (votre clé), stocké côté gateway. Vous l'**attachez** ensuite aux sandboxes.

```bash-ref
openshell provider profile import -f "$NEMOCLAW_INFERENCE_PROFILE"      # the access contract
OPENAI_API_KEY=… openshell provider create --name default \
  --type maas-openai --credential OPENAI_API_KEY                          # key held by the gateway
openshell sandbox create … --provider default                            # attach at creation
openshell provider list                                                  # never prints key values
```

Ces commandes ne sont données qu'à titre d'exemple : vous les lancerez pour de bon dans la **partie IV**, pas ici. Dans une sandbox à laquelle un provider est attaché, `$OPENAI_API_KEY` ne contient qu'un **placeholder** (`openshell:resolve:env:…`). L'agent appelle votre véritable endpoint avec cette valeur ; le proxy d'egress du supervisor la reconnaît et la remplace par la vraie clé, uniquement vers l'hôte prévu par le profile et uniquement pour ses binaires. Double avantage : l'agent **ne détient jamais votre clé**, et un placeholder volé ne sert à rien ailleurs.
