Vous venez de voir la fleet mener l'enquête. Aucune magie là-dedans : c'est un petit orchestrateur d'environ 130 lignes, intégré à ce site ([`/api/orchestrate`](/learn/incident-lab)). Cette page le présente **en entier**, sans rien cacher : le plan, le prompt exact envoyé à chaque agent, la façon dont on invoque un agent isolé et la manière dont l'agent analyst rend ses conclusions.

## 1 · Un plan fixe, sans appel au modèle pour planifier

Beaucoup d'« orchestrateurs d'agents » consomment un appel au modèle rien que pour décider de la marche à suivre. Ce n'est pas le cas ici : le plan est **fixe**, avec une probe imposée par spécialiste. Le travail intelligent revient à chaque agent, qui *exécute et interprète* sa probe, puis à l'analyst, qui en fait la synthèse. Dans les deux cas, le modèle est sollicité **via l'accès gouverné propre à l'agent**, jamais depuis le site web. Chaque probe correspond à la commande exacte que l'agent exécute :

```ts
const TQ = "node /sandbox/.agents/skills/cluster-telemetry/tq.js";
const NS = process.env.DEMO_NAMESPACE;   // your demo namespace — every probe is scoped to it
function buildProbes() {
  const ms = Date.now();
  const range = `&start=${ms - 900000}000000&end=${ms}000000&limit=15`; // last 15 min, newest first (direction=backward)
  return {
    metrics: { url: `https://<thanos>:9092/api/v1/query?namespace=${NS}&query=sum by (code) (rate(shop_requests_total{namespace="${NS}"}[2m]))`,
               hint: "request rate by HTTP code (a 5xx spike is the error rate) + average latency" },
    logs:    { url: `https://<loki>/api/logs/v1/application/loki/api/v1/query_range?query={kubernetes_namespace_name="${NS}"} |= "error"${range}`,
               hint: "the app's recent ERROR log lines (e.g. 'checkout failed: payment provider 503')" },
    events:  { url: `https://<loki>/api/logs/v1/application/loki/api/v1/query_range?query={kubernetes_namespace_name="<openshell ns>",kubernetes_container_name="event-exporter"} |= "reason"${range}`,
               hint: "recent k8s events in the demo namespace — what CHANGED (a scale-down, a deploy)?" },
    traces:  { url: `https://<tempo>/api/traces/v1/dev/tempo/api/search?q={ resource.service.name="shop" && resource.k8s.namespace.name="${NS}" && status=error }&limit=10`,
               hint: "recent ERROR traces — the failing span shows WHERE the request breaks" },
  };
}
```

Chaque probe est **limitée à votre namespace**. Le port *tenancy* de Thanos (`9092`) ne répond que pour le namespace indiqué dans `namespace=`, après avoir vérifié que l'appelant a le droit de le lire. Loki filtre sur `kubernetes_namespace_name`. Les events proviennent d'un event-exporter dédié à votre namespace de démo, et les traces portent l'attribut de ressource `k8s.namespace.name`. Dans un lab partagé, votre fleet ne voit donc jamais l'incident d'un autre participant.

## 2 · Une sous-tâche cadrée pour chaque agent

Face à une consigne vague comme « enquête là-dessus », un petit modèle s'égare : il lit des fichiers, cherche des outils et tourne en boucle jusqu'à saturer son contexte. Chaque spécialiste isolé reçoit donc une sous-tâche **cadrée**, qui contient la commande exacte à lancer. La boucle de tool calls se limite ainsi à deux appels environ (lancer la probe, puis transmettre le résultat) et se termine en une trentaine de secondes :

```ts
const subtask =
 `You are the ${a} specialist of an SRE fleet — read-only, sealed to your one backend.
  Use ONLY the exec tool. Run this EXACT command and report its output verbatim as your
  finding (it returns ${p.hint}), then briefly state what it means and STOP. Do not read
  files, do not use web_fetch or dir_list, and do NOT generate any image.

  Command:
  ${TQ} '${p.url}'

  Incident: ${task}`;
```

## 3 · Comment un agent isolé est invoqué

Chaque étape s'exécute **dans la sandbox de l'agent**, par l'intermédiaire de l'agent embarqué d'OpenClaw. Le site web n'appelle jamais de modèle : c'est la sandbox qui s'en charge, via le provider d'inférence qui lui est attaché (la sandbox ne voit qu'un placeholder, que le supervisor remplace par la vraie clé à l'egress) :

```ts
// findings are multi-line, and `sandbox exec` rejects newline args → base64 the message in,
// decode it inside the sandbox.
const b64 = Buffer.from(subtask, "utf8").toString("base64");
await openshell(["sandbox", "exec", "-n", agent, "--", "sh", "-c",
  `openclaw agent --local --json --session-id <uuid> -m "$(printf %s ${b64} | base64 -d)"`]);
```

La probe elle-même est le **skill cluster-telemetry** (`tq.js`). Il lance `curl`, un binaire autorisé en egress : l'appel reste donc encadré par la policy de l'agent, limitée à un seul backend. Il affiche ensuite un résumé *compact* pour que l'agent ne se disperse pas. Le `web_fetch` d'OpenClaw étant bloqué pour les hôtes internes, c'est ce skill qui permet à un agent isolé de lire `*.svc.cluster.local` sans rien affaiblir.

## 4 · La conclusion de l'analyst

Les agents enquêteurs travaillent **en parallèle**. Une fois qu'ils ont tous répondu, leurs constats sont transmis à l'agent **analyst**, qui n'a ni accès à la télémétrie ni tool calls. Il croise le taux d'erreur, les logs d'erreur, le span en échec et *ce qui a changé* d'après les events (`payments` passé à 0 réplica), pour en déduire une root cause (cause racine) et une remediation recommandée :

```ts
const analystPrompt =
 `You are the incident analyst synthesizing an SRE fleet's findings. Reason ONLY over the
  findings below — no tools, no files, no image, and do NOT greet or describe yourself.
  Begin directly with "ROOT CAUSE:" and cite the evidence (error rate, error logs naming the
  failing dependency, the failing span). CRITICAL: ask "what changed?" — if the events
  findings name a recent change (a dependency scaled to 0, a recent deploy) that coincides
  with when the errors began, THAT change is the root cause and the fix is to REVERSE it.
  Never state a change or an error the findings do not show. Then a FINAL line:
  RECOMMENDED_ACTION: <the specific reversal, e.g. "scale the payments deployment back up">`;
```

Toute l'exécution est envoyée en continu à la page, sous forme de JSON délimité par des sauts de ligne (`plan` → `step start/done` → `writer` → `answer`). C'est pour cela que la timeline, la requête de chaque agent et ses constats s'affichent au fil de l'eau. Un event `heartbeat` toutes les 15 s maintient la connexion ouverte pendant qu'un agent lent réfléchit encore (les load balancers des clouds coupent les connexions inactives au bout de 60 s).

Il arrive qu'un petit modèle saute le tool call ou le formule mal. Après chaque réponse, l'orchestrateur vérifie donc que le constat contient bien la sortie réelle de la probe (`status=success …` ou `traces=N`). Sinon, il exécute lui-même la même probe, **dans la sandbox de cet agent et à travers sa policy d'egress**, et retient cette sortie comme constat (*verified probe output*) en écartant le texte de l'agent : une réponse sans sortie réelle peut très bien être inventée, par exemple en reprenant l'exemple donné dans ses instructions. L'analyst raisonne ainsi toujours sur des données réelles, et la timeline indique quels constats ont eu besoin de ce filet de sécurité.

L'orchestrateur fait aussi le compte de ce que les probes ont remonté : lignes de log en erreur, traces en erreur, events récents et taux de 5xx. Si toutes les probes ont répondu et que tous ces compteurs sont à zéro, il déclare lui-même l'application en bonne santé (`synthesizedBy: evidence-check`) sans interroger le modèle, qui prendrait sinon « checkout is failing » pour argent comptant. Dans le cas contraire, l'analyst reçoit ces compteurs en plus des constats.

<Callout type="rh" title="Pourquoi cette conception">
Deux contraintes bien concrètes ont dicté ces choix. D'abord, le <code>web_fetch</code> d'OpenClaw refuse les hôtes internes : pour lire leur backend, les agents passent par un skill qui s'appuie sur <code>curl</code>. Ensuite, un petit modèle ne tient pas une boucle ReAct libre sur un gros volume de télémétrie : chaque agent reçoit donc une seule probe imposée. Le résultat est <strong>fiable et bien réel</strong> : chaque agent lance une vraie requête sur son propre backend, et la recommandation de l'analyst repose sur l'état actuel du cluster. Ce code est à vous : lisez-le, modifiez-le, adaptez-le.
</Callout>
