Cette page interroge votre **gateway en direct** : elle affiche ici la même fleet que `openshell sandbox list`, rafraîchie automatiquement à quelques secondes d'intervalle. Vous voyez ainsi d'un coup d'œil ce qui tourne, sans passer par le shell.

## Ce que vous voyez

- **Gateway OpenShell** — en vert, avec la mention « Connectée », le control plane (plan de contrôle) est opérationnel ; sa version est indiquée à côté. Il s'agit du Service de la gateway dans votre namespace (<code><Ns which="openshell" /></code>).
- **Provider d'inférence** — les providers enregistrés sur la gateway (uniquement les *noms* des clés, jamais leurs valeurs), et l'indication qu'un provider est attaché ou non à votre sandbox d'agent (`shifty`).
- **Sandboxes** — tous les agents gérés par la gateway, avec pour chacun son nom, sa phase, son état Ready, son nombre de redémarrages et son âge. Votre agent `shifty` y apparaît dès que vous l'avez créé, de même que ceux que vous créerez dans la partie VI.
- **Cliquez sur une sandbox** pour afficher son détail : un flux **Logs / audit** en direct (`openshell logs <name>`, filtrable par source, `gateway` ou `sandbox` ; c'est là qu'apparaissent les décisions allow/deny de l'egress et le handshake JWT) et le YAML de sa **Policy** complète (`openshell policy get <name> --full` : système de fichiers, processus et règles réseau par binaire). Vous retrouvez ainsi, réunies dans cette page, les informations qu'affiche la console OpenShell.

## D'où viennent les données

Le serveur du workshop tourne dans le cluster et lit donc directement ses données, sans composant supplémentaire ni interface OpenShell à déployer :

```bash
oc -n "$OPENSHELL_NS" get sandboxes.agents.x-k8s.io -o json
```

La page appelle une petite route d'API en lecture seule (`/api/openshell`), qui exécute exactement cette commande (et lit le StatefulSet de la gateway pour son état de santé), puis renvoie un JSON allégé. Comme la gateway communique en gRPC et que les sandboxes sont de simples objets Kubernetes, *n'importe quelle* interface peut afficher la fleet : la CLI `openshell`, la console associée `openshell-ui`, ou un panneau comme celui-ci, intégré à vos propres outils.

<Callout type="tip" title="À vous de l'adapter">
Ce panneau tient en 400 lignes environ (un composant React et une route d'API). Branchez-le sur des requêtes plus riches (<code>openshell policy get</code> pour chaque sandbox, l'audit log, l'egress en direct) pour construire la vue d'exploitation dont votre fleet a besoin.
</Callout>
