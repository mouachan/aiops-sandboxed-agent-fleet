Par défaut, votre agent sait *raisonner*, mais pas *chercher une information* : il n'a pas d'outil de recherche, et même s'il en avait un, le réseau deny-by-default le bloquerait. Donnons-lui la **recherche web**, gratuitement et sans clé d'API : le plugin **DuckDuckGo** d'OpenClaw extrait les résultats HTML sans JavaScript de DuckDuckGo (depuis OpenClaw 2026.8, c'est un plugin séparé à installer ; la sandbox exécute la 2026.8.2). Deux éléments doivent s'aligner : la **policy d'egress** (OpenShell) et le **plugin** (OpenClaw).

## 1. La policy l'autorise déjà

Pour chercher, le processus `node` de l'agent doit joindre les hôtes de DuckDuckGo. La policy de notre sandbox a une règle dédiée exactement à cela ; regardez le bloc `websearch` :

```bash
cd ~/workshop
sed -n '/^  websearch:/,$p' policies/openclaw-sandbox.yaml
```

```yaml
websearch:
  endpoints:
    - { host: duckduckgo.com, port: 443, access: full }
    - { host: html.duckduckgo.com, port: 443, access: full }
    - { host: lite.duckduckgo.com, port: 443, access: full }
  binaries:
    - { path: /usr/bin/node }
    - { path: /usr/local/bin/node }
```

`access: full` compte ici : un scraping HTTPS est un tunnel TLS brut, donc la règle accorde une connexion L4 complète (pas une allowlist REST analysée requête par requête) vers ces trois hôtes **uniquement**, pour `node` **uniquement**. Tout le reste reste refusé.

## 2. Installez et activez le plugin DuckDuckGo

Depuis OpenClaw 2026.8, la recherche DuckDuckGo est livrée comme plugin séparé. Installez la version qui correspond à la version d'OpenClaw de l'agent (2026.8.2 : les versions plus récentes du plugin exigent un OpenClaw plus récent) depuis le registry npm, que votre policy autorise déjà pour `node`. `--accept-capabilities` est le consentement explicite qu'OpenClaw demande avant qu'un plugin puisse faire des appels réseau pour le compte de l'agent. Choisissez-le ensuite comme provider de recherche web et **redémarrez la gateway** pour qu'elle charge le plugin :

```bash
openshell sandbox exec -n shifty -- sh -c 'openclaw plugins install @openclaw/duckduckgo-plugin@2026.8.2 --accept-capabilities; openclaw config set tools.web.search.provider duckduckgo; openclaw config get tools.web.search'
```

<Callout type="note" title="Une seule ligne, exprès">
Gardez-la sur une <strong>seule ligne</strong> (commandes enchaînées avec <code>;</code>). <code>openshell sandbox exec -- sh -c '…'</code> rejette un argument entre guillemets qui contient de vrais retours à la ligne : un bloc sur plusieurs lignes échoue avec <em>"command argument contains newline"</em>.
</Callout>

Vous verrez `Installed plugin: duckduckgo`, puis le provider relu comme `duckduckgo`. Sans le flag de consentement, la gateway refuse de démarrer (*"plugin verification failed … requires capability consent"*). Redémarrez (même commande que précédemment) :

```bash
openshell sandbox exec -n shifty -- sh -c \
  'cd /sandbox && pkill -f "^openclaw-gateway"; sleep 2; pkill -9 -f "^openclaw-gateway"; setsid nohup openclaw gateway run --port 30789 --bind lan --auth password --password '"${OPENCLAW_GATEWAY_PASSWORD:-openclaw}"' --allow-unconfigured >/sandbox/gateway.log 2>&1 < /dev/null & echo $! > gateway.pid; for i in $(seq 1 15); do sed "s/\x1b\[[0-9;]*m//g" /sandbox/gateway.log | grep -qE "\[gateway\] ready" && break; sleep 2; done; sed "s/\x1b\[[0-9;]*m//g" /sandbox/gateway.log | grep -E "\[gateway\] ready" | tail -1'
```

## 3. Faites-le chercher

Posez à l'agent une question à laquelle il ne peut répondre qu'en cherchant, et nommez l'outil : c'est ce qui pousse un petit modèle à l'utiliser de façon fiable. On exécute un tour via sa gateway :

```bash
openshell sandbox exec -n shifty -- sh -c 'cd /sandbox && openclaw agent --agent main -m "Use your web_search tool to search for: OpenShift documentation. Reply with just the domain of the official documentation site." --session-id wsdemo'
```

Il répond avec un domaine de documentation officiel (**`docs.redhat.com`** ou **`docs.openshift.com`**, selon ce que renvoie la recherche), récupéré en direct sur DuckDuckGo, à travers la policy, par votre agent scellé. Vérifiez l'egress dans `openshell logs shifty` : les requêtes vers DuckDuckGo y figurent, autorisées par la règle `websearch`. Essayez aussi dans la **Control UI** : demandez *« Quoi de neuf dans OpenShift 4.20 ? »* et regardez-le chercher.

<Callout type="note" title="Gratuit, mais toujours gouverné">
DuckDuckGo ne demande aucune clé, d'où son statut de choix par défaut. Mais remarquez que l'agent n'a pas reçu « Internet » : il a reçu <strong>trois hôtes</strong>. Si vous passiez à un provider qui appelle <code>api.bing.com</code>, l'appel serait <em>refusé</em> tant que vous n'auriez pas ajouté cet hôte à la policy. L'outil de recherche n'atteint jamais que ce que vos règles d'egress autorisent.
</Callout>

<Callout type="rh" title="Une capacité que vous pouvez auditer">
Chaque recherche est une connexion `node → html.duckduckgo.com` dans <code>openshell logs shifty</code> : autorisée, attribuée et bornée. Tout l'intérêt est là : vous donnez à un agent une vraie portée sur le monde réel sans lui ouvrir le réseau.
</Callout>
